# Rules and faction data

Step lists live in `AI_GUIDE.md` (how to add each kind of rule) and `docs/EDITING.md` (which file holds what). This
skill is the checklist around them.

## Inventory first

1. Find the card text: `public/data/factions/<ID>.json` (generated; never edit it by hand).
2. Find what already runs for it, in this order:
   - `data/abilities/<ID>.json` (key: the name, or `Name@Datasheet`), `data/stratagems/<ID>.json` (key: the card
     name in capitals, or `NAME@Detachment`), `data/detachment-rules.json`;
   - a faction module `src/factions/<faction>.ts` (`grep -n "<rule name>" src/factions/*.ts`);
   - the text reader (`src/rules-engine/abilityText.ts`, and stratagem card parsing in `stratagems.ts`), which may
     already turn the text into effects.
3. Read its line in `docs/RULES_STATUS.md` (works, partial, text only, bug).
4. Look for the same rule in another faction: copy its data shape rather than inventing one (`grep -rn "<effect key>" data/abilities`).

## Deciding

- Data before code. An `Effect` key, an `act` with a trigger, or a condition in `cond()` covers most rules.
- Code only when the rule keeps state (tokens, marks, a pool of dice): a module in `src/factions/`, registered in
  `src/factions/index.ts` through a hook from `ARCHITECTURE.md`. Never import a faction from `src/engine/` or
  `src/rules-engine/` (`src/engine/layers.test.ts` enforces it).
- A new condition or trigger is a case in `cond()` / the activation list, kept a pure function of the game state.
- Wrong datasheet numbers go in `data/overrides/<ID>.json`, then `npm run data`.

## Verify

- `npx vitest run src/engine/rulesData.test.ts`: unknown keys, conditions and triggers fail it.
- A test in the faction's test file that builds the unit and checks the number the rule changes (Hit, Wound, OC,
  Move...). For an `Effect`, the change must show in the engine (see `verify`, "Effect fields").
- For a faction-wide change, a seeded bot-vs-bot game with that faction plays to the end.
- Update `docs/RULES_STATUS.md` when a rule's grade changes.

## Pitfalls seen before

- A rule with `"status": "auto"` and no `effects` or `act` does nothing.
- A field on a timed effect is not always read the same way as on an ability (keywords such as MOBILE are only
  applied from abilities; use `throughTerrain` for a timed effect).
- Factions whose data was generated by script have more wrong numbers: check a few against the card when touching them.
- Changing the order of dice rolls changes every seeded game; if you do it on purpose, say so in the commit.
- In `scripts/build-data.mjs`, distinguish the replaced weapon from the gained item: for text such as
  "the model's lasgun is replaced with 1 laspistol", parse only the right-hand item as a choice.
- Do not trust every exported army-rule row to belong to its faction. The data export repeats Combat Doctrines for
  non-Space-Marine factions; compare the rule's faction keywords and add a regression test before regenerating
  `public/data/factions/`.
- A new phase-end activation trigger must be wired into both the turn-loop end-phase path and `AUTO_ONLY`; data
  validation alone only proves the trigger name is accepted. Test the actual reaction window through `endPhase`.
- A stratagem window can open at the right moment and still offer the wrong targets: Fire Overwatch opened at the end
  of the Movement phase and let any enemy within 24" be shot, though only a unit that moved or was set up may be.
  Check the TARGET line as well as the WHEN line, in the engine (`overwatchTargets`), the player's target list and the
  bot.
- A rule that "heals" restores wounds only to a damaged model (`heal` in `activations.ts`); with every model at full
  wounds it does nothing visible. That is not a bug in the rule (checked for Sorcerous Invigoration).
